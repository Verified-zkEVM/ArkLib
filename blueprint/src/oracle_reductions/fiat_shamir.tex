\section{The Fiat--Shamir Transformation}\label{sec:fiat_shamir}

The Fiat--Shamir transformation converts a public-coin interactive protocol into a non-interactive argument by deriving verifier messages from oracle queries. The argument prover returns a NARG string, and the verifier returns an acceptance bit. Neither algorithm returns a reduced statement or witness.

We use the public-coin IP of \Cref{def:public_coin_ip_structure}. For the salted transformations below, the NARG string consists of a salt and the prover messages.

\begin{definition}[NARG byte serialization]
\label{def:narg_serializer}
\lean{Serializer, Serializer.deserialize_eq_some_iff, Serializer.deserialize_eq_none_iff, Serializer.deserialize_append_eq_none, NonInteractiveArgument.serialize, NonInteractiveArgument.serialize_run, NonInteractiveArgument.serialize_completeness_iff}
\leanok
Let \(T\) be a typed NARG-string space, and \(B=\{0,1\}^8\) the byte alphabet. A canonical byte serializer consists of executable functions \(\NARGSerializer:T\to B^*\) and \(\NARGDeserializer:B^*\to T\cup\{\bot\}\), with
\begin{equation*}
\NARGDeserializer(\NARGSerializer(t))=t,\qquad
\NARGDeserializer(b)=t\ \Longrightarrow\ \NARGSerializer(t)=b.
\end{equation*}
Its encodings are prefix-free: \(\NARGSerializer(t)\mathbin\Vert s=\NARGSerializer(t')\) implies \(|s|=0\). Thus every nonempty suffix after a complete encoding causes rejection, including one that might otherwise encode a different value. The typed NARG-string space includes every required validity condition, such as subgroup membership or a canonical integer range. The serializer converts typed NARG strings to bytes and parses them back. It is separate from the codec, which encodes protocol messages into sponge units and decodes sponge output into verifier messages. Verifier messages are reconstructed rather than serialized in the NARG string.

\end{definition}

\paragraph{Lean correspondence.}
The security proofs use the general reduction definitions below. The conversion to a reduction supplies a dummy terminal prover output, which NARG-string generation never executes, and embeds the verifier's Boolean decision without adding oracle queries. After these output conversions, the protocol execution and both transformations agree with their reduction formulations, including oracle queries. The security hypotheses are unchanged.
\lean{InteractiveProtocol.toReduction_verdict, InteractiveProver.compileFiatShamir_eq_sendMessage, InteractiveVerifier.compileFiatShamir_eq_verify, InteractiveProver.duplexSpongeFiatShamirPayload_sendMessage, InteractiveVerifier.duplexSpongeFiatShamirPayload_verify}

In the reduction formulation, the prover computes all prover messages at once, and the verifier reconstructs the verifier messages from oracle queries on the statement and the preceding prover messages.

\subsection{Oracle Interface for Fiat--Shamir Verifier Messages}\label{sec:fiat_shamir_oracle_interface}

The key insight of the Fiat--Shamir transformation is to replace interactive verifier messages with deterministic computations based on the protocol messages so far.

\begin{definition}[Fiat--Shamir Oracle Specification]
    \label{def:fiat_shamir_spec}
    For a protocol \(\pSpec\) and statement type \(\StmtIn\), define
    \begin{equation*}
      Q_i:=\StmtIn\times\pSpec.\MessagesUpTo\;i.\mathsf{val}.\mathsf{castSucc},
      \qquad i:\pSpec.\ChallengeIdx.
    \end{equation*}
    The type \(\pSpec.\MessagesUpTo\;k\) contains only prover messages at protocol
    positions strictly before \(k\). Thus \(Q_i\) contains the statement and every preceding
    prover message, but neither verifier messages nor future prover messages.
    The oracle specification is
    \begin{equation*}
      \begin{gathered}
        \mathsf{fsChallengeOracle}\;\StmtIn\;\pSpec:
          \OracleSpec\!\left(\sum_{i:\pSpec.\ChallengeIdx}Q_i\right),\\
        (i,q)\longmapsto\pSpec.\Challenge\;i.
      \end{gathered}
    \end{equation*}
    The dependent index packages the verifier-message round and its query; the response
    has that round's verifier-message type. This specifies query and response types only.
    A sampled function table supplies deterministic, repeatable answers; choosing that
    table uniformly gives the random-oracle model. In the salted construction, oracle queries
    use \((\Instance,\SaltString)\), while the original statement remains \(\Instance\).
    \lean{ProtocolSpec.fsChallengeOracle, ProtocolSpec.srChallengeOracle, ProtocolSpec.MessagesUpTo}
    \uses{def:protocol_spec_components, def:transcript}
    \leanok
\end{definition}

\subsection{Fiat--Shamir Transformation for Provers}\label{sec:fiat_shamir_prover}

The Fiat--Shamir transformation modifies the prover's execution to compute all prover messages non-interactively while obtaining the verifier messages through oracle queries.

\begin{definition}[Fiat--Shamir Round Processing]
    \label{def:prover_process_round_fs}
    The modified round processing function for Fiat--Shamir maintains the prover messages (but not the verifier messages) and the input statement throughout execution:

    \begin{equation*} \mathsf{processRoundFS} \;j \;\mathsf{prover} \;\mathsf{currentResult} \end{equation*}

    For each round \(j\):
    \begin{itemize}
        \item If \(j\) is a verifier-message round: Run the prover's receive-step computation to obtain its state-update function, query the Fiat--Shamir oracle with the statement and preceding prover messages, then apply that function to the response
        \item If \(j\) is a prover-message round: Generate the prover message using the prover's \(\mathsf{sendMessage}\) function and append it to the prover-message history
    \end{itemize}

    The key difference from interactive execution is that verifier messages are derived via oracle queries rather than received from an interactive verifier.
    For the salted transformation below, \(\mathsf{processRoundFSSalted}\) performs the same
    round step with every oracle query keyed by the fixed context \((\Instance,\SaltString)\).
    \lean{Prover.processRoundFS, Prover.processRoundFSSalted}
    \uses{def:fiat_shamir_spec, def:prover}
\end{definition}

\begin{definition}[Fiat--Shamir Prover Execution]
    \label{def:prover_run_to_round_fs}
    The Fiat--Shamir prover execution up to round \(i\) is defined as:

    \begin{equation*} \mathsf{runToRoundFS} \;i \;\mathsf{stmt} \;\mathsf{prover} \;\mathsf{state} \end{equation*}

    This executes the prover inductively using \(\mathsf{processRoundFS}\), starting from the initial state and accumulating prover messages and the statement. Returns the prover messages up to round \(i\), the input statement, and the prover's final state.
    The salted execution \(\mathsf{runToRoundFSSalted}\) iterates the salted round step and
    carries the same context \((\Instance,\SaltString)\) through every round.
    \lean{Prover.runToRoundFS, Prover.runToRoundFSSalted}
    \uses{def:prover_process_round_fs}
\end{definition}

\begin{definition}[Fiat--Shamir Prover Transformation]
    \label{def:prover_fiat_shamir}
    In the reduction formulation, let \(\SaltLength\) be the salt length, \(U\) be the salt alphabet, and \(\mathsf{sampleSalt}:\OracleComp\;\oSpec\;(U^{\SaltLength})\) be a salt sampler using the ambient/shared oracle interface. For an interactive reduction prover \(P\), the transformation produces:

    \begin{equation*}
    \begin{aligned}
      &P.\mathsf{fiatShamirSalted}\;\SaltLength\;\mathsf{sampleSalt} :\\
      &\quad\NonInteractiveProver\;(\mathsf{FiatShamirNARGString}\;\pSpec\;U\;\SaltLength)\\
      &\quad(\oSpec\mathrel{++_\mathsf{o}}\mathsf{canonicalFSOracle}\;\StmtIn\;\pSpec\;U\;\SaltLength)\\
      &\quad\StmtIn\;\WitIn\;\StmtOut\;\WitOut
    \end{aligned}
    \end{equation*}

    The transformed prover:
    \begin{itemize}
        \item Has state type that combines the statement with the original prover's state at round 0, and uses the final state type for subsequent rounds
        \item On input, stores both the statement and initializes the original prover's state
        \item Samples one salt and sends the NARG string \((\SaltString,\IPProverMessages)\), where \(\IPProverMessages\) contains all original prover messages computed via \(\mathsf{runToRoundFSSalted}\); every verifier-message query uses context \((\Instance,\SaltString)\)
        \item Never receives verifier messages (since it is non-interactive)
        \item Retains the original terminal output function for reduction execution; the argument prover does not execute it
    \end{itemize}
    \lean{Prover.fiatShamirSalted, Prover.compileFiatShamir, Prover.runToRoundFSSalted}
    \uses{def:prover_run_to_round_fs}
\end{definition}

\subsection{Transcript Derivation and Verifier Transformation}\label{sec:fiat_shamir_verifier}

The Fiat--Shamir verifier must reconstruct the full interactive transcript from the prover messages in order to run the original verification logic.

The full transcript of a public-coin IP is defined in \Cref{def:transcript}; the basic
Fiat--Shamir transformation (\Cref{constr:basic_fiat_shamir}) fixes each of its
verifier messages as the oracle answer on the statement, the salt, and the prover messages sent
so far. In Lean, given prover messages and an input statement, \(\mathsf{deriveTranscriptFS}\)
reconstructs the full protocol transcript:

\begin{equation*}
\begin{aligned}
  &\mathsf{messages}.\mathsf{deriveTranscriptFS}\;\mathsf{stmt} :\\
  &\quad\OracleComp\;(\oSpec\mathrel{++_\mathsf{o}}\mathsf{fsChallengeOracle}\;\StmtIn\;\pSpec)
    \;(\FullTranscript\;\pSpec)
\end{aligned}
\end{equation*}

For verifier-message rounds it queries the Fiat--Shamir oracle of
\Cref{def:fiat_shamir_spec} with the statement and the prover messages up to that
point; for prover-message rounds it uses the corresponding prover message. (A salt, when
present, is carried in the statement.)

\begin{definition}[Fiat--Shamir Verifier Transformation]
    \label{def:verifier_fiat_shamir}
    In the reduction formulation, for the same salt alphabet \(U\) and salt length \(\SaltLength\), an interactive verifier \(V\) is transformed into:

    \begin{equation*}
    \begin{aligned}
      &V.\mathsf{fiatShamirSalted}\;\SaltLength :\\
      &\quad\NonInteractiveVerifier\;(\mathsf{FiatShamirNARGString}\;\pSpec\;U\;\SaltLength)\\
      &\quad(\oSpec\mathrel{++_\mathsf{o}}\mathsf{canonicalFSOracle}\;\StmtIn\;\pSpec\;U\;\SaltLength)\\
      &\quad\StmtIn\;\StmtOut
    \end{aligned}
    \end{equation*}

    The transformed verifier:
    \begin{itemize}
        \item Takes the original statement and a NARG string consisting of a salt and all prover messages
        \item Derives the transcript \((\IPProverMessages,\IPVerifierMessages)\) of
        \Cref{def:transcript} using \(\mathsf{deriveTranscriptFS}\) on context \((\Instance,\SaltString)\)
        \item Runs the original verifier's verification logic on the reconstructed transcript
    \end{itemize}
    \lean{Verifier.fiatShamirSalted, ProtocolSpec.Messages.deriveTranscriptFS}
    \uses{def:transcript, def:fiat_shamir_spec, def:verifier}
\end{definition}

\subsection{Security Properties}\label{sec:fiat_shamir_security}

The Fiat--Shamir transformation preserves important security properties of the original interactive reduction, under appropriate assumptions about the random oracle.

Completeness, with arbitrary error \(\epsilon\), is preserved as stated in \Cref{thm:basic_fs_completeness}.

\begin{remark}[Additional Security Properties]
    The remaining security properties require their own reductions. In particular:
    \begin{itemize}
        \item State-restoration knowledge soundness of the original reduction implies knowledge soundness of the Fiat--Shamir transformed reduction
        \item Honest-verifier zero-knowledge of the original reduction implies zero-knowledge of the transformed reduction
    \end{itemize}
    These results require the random oracle model and careful handling of the oracle
    programming needed for simulation and extraction. For the salted variant,
    the state-restoration reductions for soundness and straightline knowledge soundness are
    formalized in \Cref{thm:basic_fs_soundness} and
    \Cref{thm:fiat_shamir_straightline_knowledge_soundness}.
\end{remark}

\begin{remark}[Implementation Considerations]
    Our formalization models the "theoretical" version of Fiat--Shamir where the statement context and preceding prover-message prefix are hashed to derive each verifier message. In practice, more efficient variants use cryptographic sponges or other techniques to incrementally absorb transcript elements and squeeze out verifier messages. Our theoretical model provides the foundation for analyzing these practical variants.
\end{remark}
